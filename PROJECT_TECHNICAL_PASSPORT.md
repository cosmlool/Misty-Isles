- PR #15 остаётся Draft. Не сливать без отдельного разрешения пользователя. PR #14 — историческая ссылка восстановления.

## 3. Локальная установка и проверки

Использовать Node.js 22 (как в CI). Все три проекта имеют committed lockfile; установка отсутствующих зависимостей выполняется только через `npm ci`.

Полная последовательность из корня:

```bash
node tools/qa-audit.mjs

cd client
npm ci
npm run verify:project

cd ../server
npm ci
npm test
npm run build

cd ../e2e
npm ci
npm test
```

Playwright требует установленный Google Chrome и свободные порты 5173/2567. Для браузера с UI: `npm run test:headed`; для отчёта: `npm run report`.

### Единая команда VERIFY_PROJECT.bat

`VERIFY_PROJECT.bat` вызывает кроссплатформенный `tools/verify-all.mjs` и выполняет полный набор проверок:

1. Проверка обязательных файлов, JSON и согласованности всех трёх lock-файлов.
2. Установка отсутствующих зависимостей client/server/e2e только через `npm ci`; если lockfile отсутствует, скрипт завершает работу с ошибкой вместо неповторяемого `npm install`. Уже установленные `node_modules` повторно не устанавливаются.
3. Клиентские проверки, ассеты и production build через `npm run verify:project`.
4. Полный серверный набор через `npm test`.
5. Сборка сервера через `npm run build`.
6. Установка/проверка Chrome для Playwright.
7. Полные браузерные сценарии через `e2e/npm test`.

Скрипт останавливается на первой ошибке, печатает этап и команду, завершает работу ненулевым кодом. Требуется Node.js 22, как в CI.

Отдельные команды:
- Client: `npm run build` — TypeScript + Vite; `npm run verify:project` — project checks + asset audit + build.
- Server: `npm test` — последовательный запуск тестов; `npm run build` — TypeScript build.
- E2E: `npm test` — Playwright browser suite.

## 4. GitHub Actions Quality Gate

Workflow `.github/workflows/quality.yml` содержит четыре задачи:

1. **Data, docs and project structure** — `node tools/qa-audit.mjs`, включая наличие и согласованность `e2e/package-lock.json`.
2. **Client TypeScript and Vite build** — `npm ci`, затем `npm run verify:project`.
3. **Server TypeScript build** — `npm ci`, затем `npm test` и `npm run build`.
4. **Playwright browser smoke tests** — `npm ci` для server, client и e2e, установка Chrome и `e2e/npm test`; диагностические артефакты сохраняются даже при ошибке.

Все npm-проекты используют committed lockfiles и чистую установку. Для e2e lockfile создан npm 10/Node.js 22 в CI, затем чистая установка `npm ci` прошла успешно; артефакт `misty-isles-e2e-lockfile` получен и добавлен в репозиторий. Новый CI на HEAD с закреплённым lockfile обязателен.

CI — окончательная проверка изменения. Пустой список commit statuses или состояние pending не являются успехом. Проверять нужно последний HEAD PR, не старый SHA.

## 5. Сохранения и изоляция тестов

- Сервер по умолчанию использует `server/data`.
- `MISTY_DATA_DIR` задаёт отдельный абсолютный каталог; относительный путь сервер отклоняет.
- Runtime-тесты должны создавать временный каталог, копировать туда только нужные статические каталоги и удалять временную папку в `finally`.
- E2E использует синтетические аккаунты и временные сохранения; настоящая папка `server/data` не должна использоваться.
- Не запускать тесты против живого сервера или реальных аккаунтов.
- Перед изменением формата сохранений нужны анализ совместимости, миграционный тест, резервная копия/восстановление и crash/replay-тест.

## 6. Порядок дальнейшей разработки

1. Проверить актуальный HEAD PR и CI на этом SHA.
2. Прочитать паспорт и audit/checkpoint-документы; сверить их с кодом.
3. Для бага сначала получить воспроизводящий тест/сценарий, затем исправлять подтверждённую причину.
4. Не менять игровую механику в рамках инфраструктурной правки.
5. Выполнить релевантные тесты, затем полный локальный verify насколько доступна среда.
6. Зафиксировать commit и дождаться всех CI jobs. При сбое записать job, тест, сообщение, SHA и ссылку на run.
7. Сохранить checkpoint: что изменено, что проверено, что не проверено, текущие HEAD/PR/CI и следующий шаг.
8. Не удалять временные/неиспользуемые файлы до проверки импортов, ссылок, build, тестов и миграций.

## 7. Открытые технические задачи

- Сверять исторические записи в `PROJECT_AUDIT_STATUS.md` с актуальным PR и SHA: документ содержит checkpoint разных веток и периодов.
- Надёжная доставка сохранённых dungeon outbox events при входе/переподключении: pending-события, ACK после успешной доставки, дедупликация повторной доставки и crash/reconnect-тесты. Сам outbox WAL и атомарная запись результата уже созданы; доставка в клиентский канал — следующий dungeon runtime этап.
- Live `runExpeditionDungeon()` ранее оставался синхронным legacy handler; наличие durable start/round/finalization helpers само по себе не означает, что production flow полностью переключён на них.
- Реальные правила AFK лидера, spectator lifecycle и воскрешения должны проверяться отдельно по `DUNGEON_LIFECYCLE_DESIGN.md`; не считать их реализованными только по наличию документа.
- Не менять балансные коэффициенты, цены и шансы без полного аудита и согласования.
